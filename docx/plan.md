### 第一层：串口

#### 1. 先认识要打开哪个端口，以及双方约定怎样收发

例如设备说明书给出下面一组参数：

```text
COM3
115200
8 data bits
1 stop bit
No parity
```

| 示例参数 | 在这次通信中具体表示什么 |
| :--- | :--- |
| COM3 | Windows给这个串口的名称，程序据此选择要打开的端口。 |
| 115200 | 双方约定的波特率，用来设置串行传输的速率。 |
| 8 data bits | 每个传输单元使用8个数据位。 |
| 1 stop bit | 每个传输单元使用1个停止位。 |
| No parity | 不使用串口这一层的奇偶校验。 |

这组数据是示例，实际端口、参数和流控制方式要根据设备说明或模拟端约定确认，不能直接认定电脑上已经有可用的COM3。
串口的奇偶校验和数据包里的校验字段是两件事，设置No parity不表示业务协议不需要检查数据。

.NET提供的`System.IO.Ports.SerialPort`是操作串口的类，负责按参数打开端口、发送和读取数据，设备数据包的含义要由自己的代码处理；现代.NET项目使用它时需确认`System.IO.Ports`包引用，不能只写命名空间就视为依赖已具备。[Microsoft Learn：SerialPort](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport)

这一小步先做到：选定端口和参数，打开后显示成功，关闭后可以再次打开；端口不存在或被占用时给出能理解的反馈。

#### 2. 发送和接收时，先看清拿到的究竟是什么

```text
打开串口
    ↓
发送约定的数据
    ↓
接收字节流
    ↓
保存尚未处理的字节
    ↓
取出完整数据包并解析
    ↓
转换成设备读数
```

例如设备发出的数据是：

```text
AA 01 03 00 64 5F
```

这里的`AA`、`01`等每一组两位十六进制数表示一个字节，整段共有6个字节；屏幕上的空格只是为了便于阅读。
发送原始字节`AA`与发送文字`"AA"`是不同操作，文字需要按编码变成字节，因此要先区分原始数据和调试窗口显示的文字。
首次写代码时，再用完整写法解释C#的`byte`、`byte[]`、数组下标，以及接收数组中哪些位置属于本次实际数据。

`SerialPort.Read(byte[], offset, count)`把收到的数据写入指定数组，`count`表示本次最多读取多少字节，返回值才是本次实际读取的字节数；后续处理只使用这些有效字节，不能把数组中未被本次读取填入的位置也当成设备数据。[Microsoft Learn：SerialPort.Read](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.read)

#### 3. 把“一次读取”和“一个完整数据包”分开

**串口一次Read得到的数据，不一定就是一个完整的数据包。**

设备发送上面的6个字节，程序可能分三次读到：

```text
第一次：AA 01
第二次：03 00 64
第三次：5F
```

第一次只有开头两个字节，不能因为这次读取结束就把它当作一个完整包，也不能丢掉它再等下一次。
程序需要保留前面尚未处理的字节，后面有新字节时接在它们后面，这块持续保存数据的位置就是接收缓冲区。

| 本次读取 | 加上此前保留的数据后，缓冲区中的内容 |
| :--- | :--- |
| AA 01 | AA 01 |
| 03 00 64 | AA 01 03 00 64 |
| 5F | AA 01 03 00 64 5F |

反过来也可能一次读到两个完整包，或者一个完整包加上下一个包的开头，所以每次追加后要继续检查，取出当前已有的所有完整包，把剩余的不完整部分留给下一次。
上面的数据只用于说明分批到达，提示词尚未约定字段、包长规则和校验算法，不能自行认定`03`表示长度、`00 64`表示温度或`5F`是正确校验值。

这一部分的学习主线是：

```text
字节流
   ↓
接收缓冲区
   ↓
按协议取出完整包（组包）
   ↓
检查并解释包中字段（协议解析）
   ↓
设备编号、测量值、单位等业务数据
```

不把某次回调结束、等待固定时间或当前暂时没有新字节当作通用的包结束规则。
`DataReceived`是SerialPort提供的接收事件，表示有接收情况需要处理，并不保证每个字节都触发一次，更不保证触发一次就收齐一个包。[Microsoft Learn：DataReceived](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.datareceived)

#### 4. 先把包的规则写明，再实现组包与解析

程序看到`AA 01`时是否继续等待，要由设备协议决定，因此开始解析练习前先明确一份设备协议或教学协议。
协议至少要回答下面几个实际问题，相关新概念在用到时逐个解释：

- 从哪里开始一个包，例如是否有固定的开头字节，也就是帧头。
- 怎样判断已经收齐，例如固定包长或包内的长度字段，不能未经约定就套用上面6字节示例。
- 哪些字节对应设备编号、命令、测量值和单位，以及哪些取值有效。
- 一个数占多个字节时先放哪一部分，以及如何把整数换成实际测量值，例如是否需要除以10。
- 是否带校验字段，以及它覆盖哪些字节、怎样计算和比较。
- 遇到无效开头、不合法长度、校验失败或长期收不齐时，怎样丢弃无效数据并继续寻找后面的完整包。

先用人工准备的字节分段验证缓冲、组包和解析，再接串口收发，便于把“串口有没有收到”和“收到后有没有解析正确”分别观察清楚。
给缓冲区设置合理的容量与无效数据清理规则，避免设备持续发送错误数据时一直积累；只在明确协议后选择处理办法。

#### 5. 在新WPF项目中显示解析后的数据

串口收到的数组先交给组包代码，完整且检查通过的包再交给解析代码，先在控制台核对解析结果，再逐步接到新WPF窗口的读数显示与历史集合。
此前用过的Reading是练习中自行定义的读数类；后续根据协议与新项目需要确定数据类，先说明字段的用途、对象怎样创建，以及新界面怎样读取它，再要求连接。
不要直接把调试区显示的十六进制文字当成温度，也不要在数据还没收齐时就追加一条历史。

此前的DispatcherTimer.Tick用于在WPF界面线程上驱动模拟采集，SerialPort.DataReceived则在辅助线程上触发，因此接收回调中的代码不能直接照搬原来更新界面的做法。[Microsoft Learn：DataReceived](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.datareceived)
需要先解释“负责窗口操作的线程”和“负责接收的代码”各自在做什么，再学习让窗口的Dispatcher安排界面更新，把已解析读数交回界面线程后更新绑定集合和显示状态。[Microsoft Learn：WPF线程模型](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model)
接收缓冲区先由一条明确的处理路径负责修改，再结合关闭、清理和回调之间的实际关系补充并发保护，不把现有Tick实践当作已经掌握后台通信的证据。

#### 6. 把正常通信和停止后的收尾一起完成

- 未打开端口时禁止发送，打开失败时仍允许修改参数后重试。
- 接收时界面保持可操作，不能在界面线程里一直阻塞等待设备返回。
- 关闭或断开时停止本次接收流程，避免重复登记回调和重复追加读数。
- 再次打开时按约定清理旧连接残留的半包，避免把上次剩下的字节接到新数据前面。
- 设备没有回应、收发超时、端口被占用或设备断开时显示明确状态，并能在条件恢复后重新打开。
- 窗口关闭后不再更新已关闭界面，并正确关闭和释放串口占用的资源。

Task/async/await、事件和using/Dispose仍按既有[学习进度](./learning.md)保留复习范围，需要时结合当前收发和关闭流程补讲，不增加动手前的口试门槛。
已经验证的模拟读取取消链路不能直接证明实际串口读取也能按同样方式取消，后续要针对选定的读取方式实际验证停止行为。

### 串口部分的实践顺序与可观察结果

| 顺序 | 本步只解决什么问题 | 应观察到的结果 |
| :--- | :--- | :--- |
| 1 | 分清字节与显示文字。 | 能对照发送和接收记录核对原始字节及本次实际长度。 |
| 2 | 按一份明确协议处理人工分段数据。 | 相同完整数据采用不同分段方式输入，最终得到相同的包和读数。 |
| 3 | 验证缓冲与解析的边界。 | 半包保留、连续包逐个取出，无效数据按规则处理，后续有效包仍可解析。 |
| 4 | 打通端口打开、发送、接收和关闭。 | 能与选定对端核对字节，打开失败和关闭重开都有明确结果。 |

人工分段验证先使用普通字节数据，不需要串口设备；实际串口收发再按现有条件选择真实设备或可用的虚拟串口对端，设备、驱动和工具情况待确认。

- [ ] 同一份数据整包到达、分多次到达或连续多个包到达时，均能按协议得到正确且不重复的结果。

- [ ] 按已明确的字段、字节顺序和换算规则产生正确业务对象，只有有效读数才进入对应设备历史。
