### 第一层：串口

#### 1. 先认识要打开哪个端口，以及双方约定怎样收发

例如设备说明书给出下面一组参数：

```text
COM3
115200
8 data bits
1 stop bit
No parity
```

| 示例参数 | 在这次通信中具体表示什么 |
| :--- | :--- |
| COM3 | Windows给这个串口的名称，程序据此选择要打开的端口。 |
| 115200 | 双方约定的波特率，用来设置串行传输的速率。 |
| 8 data bits | 每个传输单元使用8个数据位。 |
| 1 stop bit | 每个传输单元使用1个停止位。 |
| No parity | 不使用串口这一层的奇偶校验。 |

这组数据是示例，实际端口、参数和流控制方式要根据设备说明或模拟端约定确认，不能直接认定电脑上已经有可用的COM3。
串口的奇偶校验和数据包里的校验字段是两件事，设置No parity不表示业务协议不需要检查数据。

.NET提供的`System.IO.Ports.SerialPort`是操作串口的类，负责按参数打开端口、发送和读取数据，设备数据包的含义要由自己的代码处理；现代.NET项目使用它时需确认`System.IO.Ports`包引用，不能只写命名空间就视为依赖已具备。[Microsoft Learn：SerialPort](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport)

这一小步先做到：选定端口和参数，打开后显示成功，关闭后可以再次打开；端口不存在或被占用时给出能理解的反馈。

#### 2. 发送和接收时，先看清拿到的究竟是什么

```text
打开串口
    ↓
发送约定的数据
    ↓
接收字节流
    ↓
保存尚未处理的字节
    ↓
取出完整数据包并解析
    ↓
转换成设备读数
```

例如设备发出的数据是：

```text
AA 01 03 00 64 5F
```

这里的`AA`、`01`等每一组两位十六进制数表示一个字节，整段共有6个字节；屏幕上的空格只是为了便于阅读。
发送原始字节`AA`与发送文字`"AA"`是不同操作，文字需要按编码变成字节，因此要先区分原始数据和调试窗口显示的文字。
首次写代码时，再用完整写法解释C#的`byte`、`byte[]`、数组下标，以及接收数组中哪些位置属于本次实际数据。

`SerialPort.Read(byte[], offset, count)`把收到的数据写入指定数组，`count`表示本次最多读取多少字节，返回值才是本次实际读取的字节数；后续处理只使用这些有效字节，不能把数组中未被本次读取填入的位置也当成设备数据。[Microsoft Learn：SerialPort.Read](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.read)

#### 3. 把“一次读取”和“一个完整数据包”分开

**串口一次Read得到的数据，不一定就是一个完整的数据包。**

设备发送上面的6个字节，程序可能分三次读到：

```text
第一次：AA 01
第二次：03 00 64
第三次：5F
```

第一次只有开头两个字节，不能因为这次读取结束就把它当作一个完整包，也不能丢掉它再等下一次。
程序需要保留前面尚未处理的字节，后面有新字节时接在它们后面，这块持续保存数据的位置就是接收缓冲区。

| 本次读取 | 加上此前保留的数据后，缓冲区中的内容 |
| :--- | :--- |
| AA 01 | AA 01 |
| 03 00 64 | AA 01 03 00 64 |
| 5F | AA 01 03 00 64 5F |

反过来也可能一次读到两个完整包，或者一个完整包加上下一个包的开头，所以每次追加后要继续检查，取出当前已有的所有完整包，把剩余的不完整部分留给下一次。
上面的数据只用于说明分批到达，提示词尚未约定字段、包长规则和校验算法，不能自行认定`03`表示长度、`00 64`表示温度或`5F`是正确校验值。

这一部分的学习主线是：

```text
字节流
   ↓
接收缓冲区
   ↓
按协议取出完整包（组包）
   ↓
检查并解释包中字段（协议解析）
   ↓
设备编号、测量值、单位等业务数据
```

不把某次回调结束、等待固定时间或当前暂时没有新字节当作通用的包结束规则。
`DataReceived`是SerialPort提供的接收事件，表示有接收情况需要处理，并不保证每个字节都触发一次，更不保证触发一次就收齐一个包。[Microsoft Learn：DataReceived](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.datareceived)

#### 4. 先把包的规则写明，再实现组包与解析

程序看到`AA 01`时是否继续等待，要由设备协议决定，因此开始解析练习前先明确一份设备协议或教学协议。
协议至少要回答下面几个实际问题，相关新概念在用到时逐个解释：

- 从哪里开始一个包，例如是否有固定的开头字节，也就是帧头。
- 怎样判断已经收齐，例如固定包长或包内的长度字段，不能未经约定就套用上面6字节示例。
- 哪些字节对应设备编号、命令、测量值和单位，以及哪些取值有效。
- 一个数占多个字节时先放哪一部分，以及如何把整数换成实际测量值，例如是否需要除以10。
- 是否带校验字段，以及它覆盖哪些字节、怎样计算和比较。
- 遇到无效开头、不合法长度、校验失败或长期收不齐时，怎样丢弃无效数据并继续寻找后面的完整包。

不要直接把调试区显示的十六进制文字当成温度，也不要在数据还没收齐时就追加一条历史。

此前的DispatcherTimer.Tick用于在WPF界面线程上驱动模拟采集，SerialPort.DataReceived则在辅助线程上触发，因此接收回调中的代码不能直接照搬原来更新界面的做法。[Microsoft Learn：DataReceived](https://learn.microsoft.com/en-us/dotnet/api/system.io.ports.serialport.datareceived)

#### 6. 把正常通信和停止后的收尾一起完成

- 未打开端口时禁止发送，打开失败时仍允许修改参数后重试。
- 接收时界面保持可操作，不能在界面线程里一直阻塞等待设备返回。
- 关闭或断开时停止本次接收流程，避免重复登记回调和重复追加读数。
- 再次打开时按约定清理旧连接残留的半包，避免把上次剩下的字节接到新数据前面。
- 设备没有回应、收发超时、端口被占用或设备断开时显示明确状态，并能在条件恢复后重新打开。
- 窗口关闭后不再更新已关闭界面，并正确关闭和释放串口占用的资源。

Task/async/await、事件和using/Dispose仍按既有[学习进度](./learning.md)保留复习范围，需要时结合当前收发和关闭流程补讲，不增加动手前的口试门槛。
已经验证的模拟读取取消链路不能直接证明实际串口读取也能按同样方式取消，后续要针对选定的读取方式实际验证停止行为。

### 1. 先让上位机找到设备模拟器

```text
C#控制台上位机 → 后续接入C# WPF
          │
          │ TCP：命令与回复
          ▼
设备模拟器：Java或C#控制台程序
```

模拟器先在本机地址和一个约定端口等待连接，上位机按同一地址和端口发起连接。
例如`127.0.0.1:5000`中，`127.0.0.1`表示当前这台电脑，`5000`表示模拟器准备接收连接的TCP端口；它只是教学示例，开始时要确认端口可用。
在这个场景中，主动连接的上位机是TCP Client，监听并接受连接的模拟器是TCP Server；连接建立后双方都可以发送和接收数据。

先用.NET提供的`TcpClient`连接模拟器，用连接上的`NetworkStream`发送和读取字节。
如果模拟器用C#实现，则由.NET的`TcpListener`负责监听和接受连接；监听对象与接受后用于和某个上位机收发的连接对象分别说明，避免把二者混为一谈。[Microsoft Learn：TCP通信类](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/sockets/tcp-classes)

先做到控制台两端能建立连接、完成一次命令往返、主动关闭并再次连接，再把同一通信逻辑接入WPF。
初期只处理一个上位机与一台模拟设备，先把收发和停止做清楚；多客户端并发不作为本阶段起步条件。

### 2. 用一份明确的命令协议控制模拟设备

下面是本阶段拟采用的教学协议，不是真实设备的通用协议，也不沿用串口的AA开头六字节帧。
双方统一使用不带BOM的UTF-8编码，每条TCP命令和回复以一个LF换行字节结束；下表中的`\n`表示这个实际换行，不是发送反斜杠和字母n。
初期命令和回复只使用表中的英文字符与数字，一条消息内部不包含换行，温度小数点统一使用`.`。

| 上位机发送 | 模拟器回复示例 | 应观察到的结果 |
| :--- | :--- | :--- |
| `GET_TEMP\n` | `35.6\n` | 上位机获得一个温度值，WPF接入后显示35.6℃并追加一条有效历史。 |
| `START_DEVICE\n` | `OK\n` | 模拟器把设备状态设为运行，上位机收到确认后显示成功。 |
| `STOP_DEVICE\n` | `OK\n` | 模拟器把设备状态设为停止，上位机收到确认后显示成功。 |
| `GET_STATUS\n` | `RUNNING\n`或`STOPPED\n` | 查询模拟器保存的状态，核对启动和停止是否实际生效。 |
| `PING\n` | `PONG\n` | 在后续心跳步骤中检查模拟程序是否能按协议回应。 |
| 未约定的命令 | `ERR_UNKNOWN_COMMAND\n` | 显示协议错误，不生成温度历史，也不显示控制成功。 |

前三条来自你提供的提示，状态查询、心跳和错误回复是为验证控制结果与异常恢复新增的教学约定，使用前分别解释。
模拟器必须保存实际运行状态，启动和停止后能通过查询核对，不能只在上位机本地更改成功文字。
设备停止运行与TCP连接关闭是两件事，本教学协议约定停止后仍可查询温度和状态；模拟温度可以先固定为35.6，再在需要时增加变化样例。

初期一条连接同一时间只等待一条请求的回复，普通命令、温度轮询和心跳共用这一顺序，不能让它们各自读取同一个连接并争抢回复。
若以后需要同时等待多条请求，再解释请求编号及回复对应规则，本阶段不把并发请求协议作为前置要求。

### 3. 收到一批字节后，按换行取出完整消息

例如模拟器回复`35.6\n`，上位机可能先读到`35`，随后才读到`.6\n`；也可能一次读到`35.6\nOK\n`两条完整回复。
因此一次发送和一次读取不保证与一条业务消息对应，常说的“粘包/拆包”在这里要靠双方约定的换行边界处理，不能靠增加等待时间解决。

```text
收到：35          → 保存，尚未遇到换行，不产生温度读数。
再收到：.6\n      → 取出35.6，转换并产生一条温度读数。
收到：35.6\nOK\n  → 依次取出35.6和OK，分别交给对应处理。
```

上面最后一行用于说明解析器面对连续消息的行为，实际请求回复仍遵守一次只等待一条的约定。
复用已验证的缓冲思路，但把“够六字节且AA开头”的判断换成本协议的换行规则；每次只追加实际读取的有效字节，循环取出所有完整消息，把末尾不完整部分保留。
先按字节找到完整消息，再按约定编码解码；后续若扩展中文内容，也不能把每批可能截断字符的字节直接独立解码后拼接。
在对应实践中明确最大消息长度、缓冲上限、空消息和错误内容的处理规则，避免对端一直不发换行时无限积累。

`NetworkStream.ReadAsync`的返回数量表示本次实际读到多少字节，不承诺读满数组；请求读取的长度大于0时，返回0表示对端已正常结束发送且可读数据已读尽，应结束本次接收并按本项目约定清理连接，不能把它当作“暂时没数据”继续空转。[Microsoft Learn：ReadAsync](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.networkstream.readasync?view=net-10.0)
模拟器分多次写入不保证上位机一定分同样次数读到，因此验证时同时保留两端实际收发日志与人工分段输入，分别核对真实往返和解析边界。

### 4. 把网络结果接入已有WPF监控能力

窗口逐步提供地址、端口、连接、断开、读温度、启动设备和停止设备操作，并显示连接状态、设备状态、最新温度和通信日志。
使用已验证的历史、曲线和报警呈现有效温度，通信代码先负责收到和解析消息，界面再负责显示结果，不把TCP收到的每一批字节都当作一次温度采样。
“启动设备”发送远端命令，“开始采集”定时查询温度，“断开连接”结束通信，三个动作的对象不同，按钮和状态说明要分别写清楚。

连接和接收采用异步流程，等待模拟器回复时窗口仍能移动、点击停止或关闭；异步与取消的具体写法按已有待复习范围在使用处补讲。
从接收流程更新WPF控件或绑定集合时，先解释当前代码在哪个线程执行，再通过合适的窗口线程更新路径连接，不照搬串口DataReceived的触发方式。
每条连接只保留一条负责读取的流程，连接重建后使用新的缓冲和等待状态，旧连接已经排队的界面通知不能改写新连接的状态或历史。

### 5. 模拟器没有及时回复时，区分超时、断开和恢复

| 实际现象 | 本阶段要处理的行为 |
| :--- | :--- |
| 模拟器未启动、地址或端口不对。 | 连接失败或连接等待到期后给出明确结果，允许修改参数后重试。 |
| 连接建立了，但当前命令一直没有完整回复。 | 按请求截止时间结束等待，显示请求超时，不将发送成功显示为设备执行成功。 |
| 模拟器正常关闭连接，或收发发生网络错误。 | 停止本连接的接收、轮询、心跳和等待，记录原因并释放资源。 |
| 对端程序仍在，但故意不再回复心跳。 | 按约定的心跳等待规则判定本次通信不可用，进入统一清理与恢复流程。 |
| 用户主动断开或关闭窗口。 | 取消接收与重连等待，释放连接，不再自动恢复或更新已关闭窗口。 |

连接超时、单条请求的响应超时、心跳无回应分别解决不同等待，不能用同一个“读取超时”名称代替全部规则。
`NetworkStream.ReadTimeout`只影响同步读取，不控制`ReadAsync`；异步实现要根据所用方法落实取消和截止时间，并核对超时后旧读取确实结束，不能只停止界面上的等待。[Microsoft Learn：ReadTimeout](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.networkstream.readtimeout?view=net-10.0)

先实现手动重新连接，再增加可以停止的自动重连：每次失败先清理旧连接，按约定间隔等待后尝试，防止多个重连流程同时运行；等待间隔与停止规则在实践前明确。
初期没有请求编号，某条请求超时后先结束旧连接，再允许新连接发送下一条请求，避免迟到的`OK`被当成新请求的回复。
控制命令超时只说明没有按时收到确认，设备可能已经执行；恢复后先查询状态，不自动重发上次启动或停止命令。

心跳从一个具体行为学习：连接空闲时发送`PING`，在约定时间内等`PONG`；有业务请求等待时先遵守同一条请求顺序，避免心跳抢走业务回复。
心跳用于确认模拟程序还能回应，TCP连接建立过不等于它此刻仍然可用；`Socket.Connected`反映最近一次操作的连接状态，不能单靠它判断当前对端存活。[Microsoft Learn：Socket.Connected](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.socket.connected?view=net-10.0)
让模拟器提供延迟回复、不回复、正常关闭连接和重启等可控场景，用实际结果核对等待、清理和恢复；这些本机故障场景分别记录，不把它们等同于所有真实网络故障都已覆盖。

### 6. 在同一收发场景中认识Socket

当上位机已经能通过`TcpClient`通信后，再沿着现有连接解释`Socket`：它是.NET提供的网络通信类，负责连接及字节收发，`TcpClient`和`TcpListener`内部使用它完成TCP通信。[Microsoft Learn：TCP与Socket的关系](https://learn.microsoft.com/en-us/dotnet/fundamentals/networking/sockets/tcp-classes)
用一段与既有命令往返对应的最小`Socket`收发对照，认识连接、发送、接收和关闭各自操作哪个对象；直接使用发送方法时还要按返回数量处理未发送完的数据。
这一部分用于理解已有程序下面的连接对象及API选择，不要求把WPF通信系统全部改写成另一套实现，也不提前引入高性能网络框架。

### 7. 用UDP完成一次独立的设备查询

TCP主线稳定后，再用.NET提供的`UdpClient`向模拟器发送一个查询数据报，并接收带有来源地址和端口的回复，从同一台模拟设备观察UDP的区别。
UDP保留数据报边界，不把多个数据报直接套进TCP的连续字节缓冲中寻找换行；它不保证送达、顺序或不重复，程序要能处理没有回复、重复和过期回复。[Microsoft Learn：UDP通信](https://learn.microsoft.com/en-us/dotnet/framework/network-programming/using-udp-services)

这一小部分先做单播查询，在对应实践中明确查询编号、回复内容、长度上限和等待期限；模拟器把收到的查询编号带回，上位机只接受约定来源且编号匹配的回复，同一编号只完成一次等待。
通过模拟端主动不回复、重复回复和延迟旧回复来验证超时与过滤，不依赖本机网络恰好出现丢包或乱序。
初期UDP只做温度或状态查询，TCP继续承担主线控制；广播设备发现可作为后续扩展，暂不要求自行实现一套可靠UDP传输机制。
