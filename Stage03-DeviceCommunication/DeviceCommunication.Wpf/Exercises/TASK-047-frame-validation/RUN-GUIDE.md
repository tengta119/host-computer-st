# TASK-047：让坏数据不能冒充温度读数

本题保留TASK-046的等待、超时、断开、历史、曲线和报警，只在生成读数前增加协议检查，并让坏数据后面的好帧仍能被找到。
核心实现只有两处：Task047Protocol.cs的TODO 1判断一帧是否合法，Task047SerialConnection.cs的TODO 2处理不合法候选后怎样继续寻找下一帧。

## 先看这次真正要检查的字节

模拟端发送下面这六个字节，应当表示设备1的25.0℃读数。

```text
AA 01 03 00 FA A8
```

| 下标 | 内容 | 本题要求 |
| --- | --- | --- |
| 0 | AA | 固定开头。 |
| 1 | 01 | 设备只能是01或02。 |
| 2 | 03 | 本题只接受03温度读数命令。 |
| 3、4 | 00 FA | 前一个字节乘256，再加后一个字节，得到原始250；只接受0至1000。 |
| 5 | A8 | 必须等于前五个字节相加后除以256的余数。 |

AA、FA和A8是十六进制写法，分别对应十进制170、250和168；数组里的byte保存数字，X2只是把这个数字显示为两位十六进制文字。
前五个数相加是170 + 1 + 3 + 0 + 250 = 424，424除以256的余数是168，所以末字节必须是A8。
发送端算一次并放进末字节，接收端根据自己收到的前五字节再算一次，两者不一致就拒绝这帧，这就是本题使用的简单加和校验。
它不是CRC，也不能保证发现所有错误，例如两个字节一增一减时加和可能不变；本题不把它当成真实设备标准。

在C#里，下面两行只演示“加和”和“取余”，不是整个验证方法的答案。

```csharp
int sum = 170 + 1 + 3 + 0 + 250;
int expected = sum % 256;
```

sum和expected是这段例子自行命名的局部变量，int是C#整数类型，%是C#取余运算符，expected最终是168。
放进实际方法时，前五个数来自frame[0]至frame[4]，用int保存相加的结果，避免把大于255的总和直接塞进byte；算出的余数再与frame[5]比较。
原TASK-044示例末字节5F不符合这份新规则，本题必须用专用模拟端，旧TASK-044至046协议和文件保留。

## 第一处：完成IsValidFrame并观察第一条合法读数

打开同目录Task047Protocol.cs，完成TODO 1。
Task047Protocol是教练为这题新建的普通类，IsValidFrame也是教练命名的普通方法，它接收一份byte[]数组，返回bool：true表示符合本题规则，false表示拒绝。
它不打开串口、不修改表格、不控制等待，只判断收到的六字节数据；Task047SerialConnection中已有_protocol字段创建并保存了一个Task047Protocol对象，接收处理会调用_protocol.IsValidFrame(frame)。
frame是这个方法的参数，调用时传进来的数组已经复制了缓冲开头六字节；长度检查由教练提供，字段与校验判断留给你。
例如命令不对时可以明确拒绝：

```csharp
if (frame[2] != 0x03)
{
    return false;
}
```

0x03是C#十六进制数字写法，!=表示不等于，上面只处理命令这一项；你还要按表检查开头、设备、原始值和加和，全部符合时才返回true。
设备合法的意思是“等于1或者等于2”，拒绝的意思是“既不是1，也不是2”，写条件前先对照这两个具体数，避免把逻辑方向写反。
原始值继续使用frame[3] * 256 + frame[4]，温度除以10.0由复用的读数类处理，不要把frame[4]单独当成完整温度。

首个动作是只完成TODO 1，运行两端并在模拟端输入1，预期窗口历史新增设备1、25.0℃，之后输入5至8不应新增读数。
在TODO 1完成前，方法固定返回false，所以骨架收到任何完整候选都不会追加历史，请求等待会按已有逻辑超时，这不是串口没收到的证明。
TODO 2尚未完成时，单独好帧可以显示，但同一批坏数据后面的好帧仍可能被占位处理丢弃，不能据此视为本题通过。

## 第二处：坏候选后继续寻找好帧

打开Task047SerialConnection.cs的ExtractReadings，找到TODO 2；复制六字节、调用验证和合法帧的消费/生成读数已连接，不用重写。
这里的“候选”只表示“缓冲开头AA后已经有六字节，值得拿出来检查”，还不能说明它就是合法的温度帧。
看下面一批实际字节：

```text
AA 99 AA 01 03 00 FA A8
```

第一次拿到的六字节是AA 99 AA 01 03 00，它不合法，但其中第3个字节AA恰好是后面好帧的开头。
如果一次删掉前六个字节，就只剩FA A8，好帧已经丢了；如果删掉当前最前面的一个AA，接着跳过99，就重新遇到AA 01 03 00 FA A8，能够检查并输出25.0℃。
因此TODO 2只在这份候选不合法时丢掉缓冲第一个字节，再继续同一个while循环；合法时仍按已有代码一次消费六字节并生成一条读数。
当前Clear和break是骨架的安全占位，防止未完成时死循环或无限积累，TODO 2需要替换这两行；它们会丢掉这批后续数据，不是正确恢复实现。
合法帧AA 01 03 00 AA 58里面的第5字节AA是原始值170的一部分，验证通过后整帧消费即可，不能一遇到内部AA就从那里重新开始。
两处完成后，每轮不是删掉无效字节，就是取走一个合法六字节帧，或者不足6字节就停下来等下一次追加，因此处理结束最多保留5个未完成字节；这就是本题缓冲不会一直增长的依据。

## 已有收发与等待怎样接上

接收辅助仍把本次Read返回的有效数量追加进同一个缓冲，ExtractReadings只把合法完整帧转成Task045Reading，再由已有ReadingReceived和Dispatcher送回窗口。
坏帧没有读数通知，所以不会进入历史或结束请求等待；有效读数才会调用窗口原有的EndWaiting，没有有效回复仍按3秒超时。
完整帧可能在一次Read或多次Read里到达，模拟端一次Write也不保证窗口只触发一次接收，因此不要依赖发送菜单与接收事件一一对应。
重连前清缓冲、旧连接编号保护与窗口关闭收尾直接复用TASK-046，两个TODO都不需要另造事件、线程或计时器。

### TODO 2具体替换哪两行

2026-10-20用户询问如何完成TODO 2，当前拒绝分支仍是教练提供的Clear/break占位，下面给这处局部写法说明，不直接代改源码。
在if (!_protocol.IsValidFrame(frame))内部，把_receivedBytes.Clear()换成_receivedBytes.RemoveAt(0)，把break换成continue。

```csharp
if (!_protocol.IsValidFrame(frame))
{
    _receivedBytes.RemoveAt(0);
    continue;
}
```

_receivedBytes是当前连接保存接收字节的List<byte>对象，RemoveAt是.NET列表的方法，参数0表示只删除现在第一个元素；这里前面已确认第一个字节是AA，所以删掉的就是这个未通过检查的候选起点。
continue是C#循环语句，跳过本轮下面的读数生成代码，回到while开头重新判断剩下的数据；它不退出整个循环，区别于当前占位的break。
例如收到AA 99 AA 01 03 00 FA A8时，首个六字节候选不合法，删掉第一个AA后剩99 AA 01 03 00 FA A8；回到while后已有“不是AA就删首字节”的代码会删99，剩下AA 01 03 00 FA A8再接受检查，合法才生成25.0℃。
若用Clear会同时删掉后面的好帧，若用break则停止本批继续查找；保留合法分支原有RemoveRange(0, 6)和readings.Add，只替换拒绝分支这两行即可。
